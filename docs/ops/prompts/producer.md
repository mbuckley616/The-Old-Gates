## What changed and why
- Removed the override (eight points) and rewrote the body to it. 30,000 characters become 19,000.

- The orphan rule counted no card in "review", so it would lift a freeze two hours after a card finished even while its PR still waited. Now a card in review with its PR open counts.

## 2. Approvals: merge exactly what he approved
A merge approval arrives as: the card set "approved" on the board (it then carries `approved_sha`); a reply of approve/merge/yes in the merge's Slack thread; a ✅ reaction on that message; or a top-level message naming the branch ("approve systems", "merge both"). A merge card that is back at "ready" was undone: do nothing. The approved commit is the target T = `approved_sha`; if it is empty (a card from before the page recorded it), T = `git rev-list -1 --before=<approved_at> origin/<branch>`, written to the card as `approved_sha` before you go on. Never merge anything later than T; commits the builders pushed after T wait for their own card and approval.
For each approved card, in the same run, with no waiting on the builder:
1. Check T: the check runs on T are green (a merge-anyway decision skips this), and T merges cleanly onto origin/main (scratch: `git checkout -q --detach origin/main && git merge --no-commit --no-ff T`, then `git merge --abort`). A conflict, or CI red without a merge-anyway: set the card "blocked" with the reason and an `Unblocks:` line, raise the stall for Michael (below), stop for this card. CI still running on T: leave it "approved" for the next run.
2. If the PR's head is still T: merge the PR with the GitHub MCP merge tool, merge method "merge", passing T as the expected head sha so nothing newer can slip in.
3. If the branch has moved past T: on auto/producer (up to date with origin/main), `git merge --no-ff T -m "Merge approved <approved_title> (<T first 7>), approved by Michael <date>"`; run `python3 scripts/parsecheck.py` (it must pass; if it does not, abort the merge, block the card with the reason and stop); push auto/producer; make sure the `Producer` PR is open; then merge that PR with the GitHub MCP merge tool, passing its head sha, as soon as its check runs are green. The suite takes up to 45 minutes on GitHub's runners: check every two minutes for up to 10 minutes, and if it has not finished, leave the card "approved" and finish it next run (T stays pinned; a later run merges the same Producer PR head once green).
4. Verify: `git fetch origin && git merge-base --is-ancestor T origin/main`. Then set the card "merged" with merged_at and `merged_sha` = T; reply once in its Slack thread (outside quiet hours) `Merged <Systems sessions NNN–MMM> to main; the site rebuilds in a few minutes.`; refresh `meta/build`.
5. If the GitHub merge is refused from this environment, leave the card "approved" and add a `blockers` card "Cloud cannot merge" with the error text; Claude (local) picks it up.
After a merge, if the branch has commits beyond T, the same card starts a new cycle: status "ready" (if CI is green on the new head) with the new `head_sha`, title, summary and `updated`, and approved_*, merged_* and `slack_ts` cleared, which gives it a fresh Slack post.
