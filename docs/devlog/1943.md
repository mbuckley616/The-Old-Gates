## v80 — Session 1943 — the game fills the window, and the edges stop stretching (backlog E; Michael, 18 Oct 2026)
*Numbered 1943: the look builder's run took 1942 first (PR #1241). The branch keeps its name, `auto/systems-1942`.*
The run's first item. Section I holds nothing for the systems builder, every finding in `docs/quest_review.md` is applied, and every
answer Michael gave this lane on 6 Nov is built (#1201 in 1933, #1211 in 1934, #1225 in 1935, #1202 in 1939–1940). The core loop's
sheets are built to their last owed line, and what is left of them waits on someone else's words or pieces (the Register, the Mouth,
the first-time lines). So this takes backlog E's unstruck request from the control room, which needs no design:

> "Can we work towards the game not being on super-widescreen mode? Or at least make sure that is being addressed in the 2.0 build
> of this game? We dont fill the browser window the same way we do for the Airsoft game, and the edges get really stretched/warped."

**What was wrong.** One line of `index.html`'s CSS: `#g`, the game's frame, was `width:100%; height:600px`. It is 600 px high at any
window size, a leftover from the page's first life embedded in a chat. So on a desktop browser the game was a strip: 1920 wide by 600
high in a 1920×950 window, aspect 3.2, the rest of the window black. The camera's field of view is vertical (75°, `CAM` in
`10-player.js`), so a strip that wide spreads it to 136° across. That is the warp at the edges, a fish-eye stretch that grows with the
window's width: 117° in the tests' 1280×720 window, 146° in a 2560×1080 one.

**What changed.** `#g` is now `height:100vh` (and `100dvh` where the browser has it, so a phone's address bar doesn't hide the bottom),
with its 8 px rounded corners gone, since it meets the window's edge now. Nothing sits below `#g` on the page, so nothing is pushed
off. `resize()` already reads the frame's own size and sets the camera's aspect on each window resize, and the settings sheet's
Field of view row (60–100, S691) and the sprint and lunge widenings still move the vertical figure as before. No rule of play
changed; no code in `js/`.

### Verified (headless Chromium)
A throwaway check booted the game and resized the window, before the change and after:

| window | before: canvas, aspect, across | after: canvas, aspect, across |
|---|---|---|
| 1280×720 | 1280×600, 2.13, 117° | 1280×720, 1.78, 108° |
| 1920×950 | 1920×600, 3.20, 136° | 1920×950, 2.02, 114° |
| 2560×1080 | 2560×600, 4.27, 146° | 2560×1080, 2.37, 122° |
| 390×780 (a phone) | 390×600, 0.65, 53° | 390×780, 0.50, 42° |

The drawing buffer follows (`1920×950` at a pixel ratio of 1), the page never scrolls, 0 page errors.

  retry. Its first try timed out a screenshot at 120 s with four boots sharing this machine (Hearthwick unseen after 82 s); the larger

**For the suites.** They boot at 1280×720, so every suite's canvas grows from 1280×600 to 1280×720: 20% more pixels on software GL,
and 9° less across. A suite that counts what is in view may count a little less; none of the smoke set measures it.

### Needs eyes
- At 1920×950 the view is now 114° across. A 16:9 monitor's full screen gives 108°. If an ultrawide (21:9) window still reads as
  stretched at 122°, the usual fix is to hold the view across at its 16:9 width and narrow the vertical instead (Hor+ capped at
  16:9). That is a number a player feels, so it is not built here; the settings' Field of view row can already bring it down.
- The phone: the frame is now the whole screen in portrait, 42° across. The touch controls sit where they did against the frame's
  bottom, which is now the screen's bottom.
