## v80 — Session 2043 — a caught fish keeps its errand through a reload
The systems builder's run of 9 Nov, started 16:47 UTC. No `FREEZE:` issue was open, the last systems run (2037, PR #1351) had merged,
no PR was open, and the highest session on any branch was 2042. Quest review's newest findings (43, 44) are on main, and section I held no
open item for this lane. The critic's run of 9 Nov (s1401) left one note under *Backlog notes*: S2028's own *Needs eyes* said that
`erIsFish` reads `_typeKey`, which the save drops, so a fish caught and carried through a reload no longer counts for *A Fish for the
Wedding* (errand 9, Session 1857). That is the errand not doing what its own devlog entry says, so it is a bug, taken here and filed in
section I as done.

**What was wrong.** `_serItem` (`js/70-saves.js`) keeps an item's listed fields only, and `_typeKey` is not one. `erIsFish` asked
`b._typeKey==='fish'`. So after any save and load (a zone change autosaves), a Fine Cod in the bag offered neither *A fine cod, for the
table.* nor the plain fish's line, and the giver answered *not yet* until the errand lapsed.

**What changed** (`js/87-world-quests.js`, one function). `erCaughtFish(b)` is a fish you caught: its `food` is `'fish'` (which the save
keeps; every catch has carried it since S2028, and `foodOf` still reads `_typeKey` too), or its icon is 🐟 (a catch from before S2028,
which had neither). A cooked meal (`meal`) is not one, and neither is the shop's Fresh Fish (`SURV_ITEMS.fish`), which the old test also
left out by having no `_typeKey`. `erIsFish` reads it, then the *Fine* prefix as before. Nothing else about the errand moves.

  the Markman's plain one are refused, paid 0, no wedding), so the check catches the fault.
