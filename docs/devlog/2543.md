## v80 — Session 2543 — a load in the water: the fallback the code named was never there
The systems builder's run of 22 Nov (22:47 UTC), on `auto/systems-2543` from origin/main at s1871. No `FREEZE:` issue was open, the last
systems branch (#1906) had landed, and `docs/quest_review.md` lists nothing new since its clean run 54. Section I holds nothing more for
this lane: the weekly run's four were struck by Sessions 2537–2540. The one open systems decision (#1883, workstations) still waits, and
every answered one is built (backlog B, C and L read through: naval combat B, the cloak's den, water, camp, magic B, the co-op half). So
this run is a bug hunt in the lane's files, as Sessions 2508, 2516 and 2523 were.

**How it was found.** Two sweeps came back clean and are worth recording as such. ESLint's correctness rules (duplicate keys and cases,
`valid-typeof`, unreachable code, self-assignment, constant conditions, `no-dupe-else-if`) over the eighteen files of this lane gave 8
hits, none a fault: dead legacy code after an early `return` in `touchSigil` and `tryLockpick` (marked as such), a `WORLD` export listing
five names twice with the same value, and `updateHUD`'s second `lid==='overworld'` branch, which the first covers. Every `worldState` key
the game writes (108 of them) is read back by `_applyLoadData`. The co-op rule's outcome rolls left on `Math.random` in this lane are
cosmetic (rumours, barks, sparks) or dead (`readScroll`, the old `bpick`).

The third sweep found the fault: every `WORLD.<name>` the game reads, against the names the `WORLD` object exports. Two are read and were
never exported: `WORLD.lastWorldPos` (twice in `70-saves.js`) and `WORLD.spawn` (once). Neither exists in any build: `git log -S` finds
them only in the first stamp of the split files.

**What was wrong.** `_applyLoadData`'s restore by place has a guard: *an old save made indoors carries interior coordinates as if they
were the world's — never trust a position in the sea*. A position in the water was to fall back on `WORLD.lastWorldPos`, then on
`WORLD.spawn`, and only then on the save's own `px`/`pz`. With the first two undefined, it always took the last: the very spot it had
just refused. So:
- an old save made in a room (no `where` beside its `px`/`pz`) loaded you at the room's coordinates in the open world: (6.5, 4.2), the
  map's corner, swimming in the sea;
- every save in the water that names its place, at the helm or swimming, was "refused", then put back on the same spot with its yaw set
  to 0, so you came back facing north.

**What changed.**
- `js/70-saves.js`: a position in the water is trusted when the save names its place (`d.where`): you were in the world there, aboard
  or swimming, and it keeps its yaw. Without `where` (a save from before places were saved), a position in the water, or one with no
  finite x and z, starts you at the game's own start, the spot on the road out of Ashenmoor that a new game uses. The `where` builder's
  last line, which returned `WORLD.lastWorldPos` and so always returned nothing, is gone (it returns `null` as before).
- `js/88-world-ticks.js`: `WORLD.spawn`, a getter that builds the world if it is not built (`build()` lays the home cell at once, and with
  it the road spawn) and returns a copy of `spawn`: what the load had been reading all along.
