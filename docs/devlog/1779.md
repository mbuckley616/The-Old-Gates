## v80 — Session 1779 — `g.settle` asks for the cells on every poll (QA, pipeline)
QA's run of 3 Nov, 06:50 UTC. No freeze was open, QA's newest branch (`auto/qa-1770`) had landed as #1054, and no `check` run had
failed since QA's last run: the three reds of 2 Nov (`f4animals` on two branches, `yardpanel`) were each on a branch whose next
push went green and landed, so they were the changes' own. Main's weekly reds of 1 Nov are all filed or fixed (section I, line 457).
So this run lands the harness fix Session 1771 wrote and held back, because a pipeline change goes in its own run's PR.

**The fault, the harness's.** `g.settle(id)` (`tests/lib/game.mjs`, used by 240 suites) moves you to the site and runs the world's job
queue each 2.5 s poll, but never asked for the cells. The game asks for them (`tickCells`) only every 0.75 s of world time, on its own
frames, and under load those come seconds apart, so the site's cell could stay unqueued and the queue run empty for the whole wait.
That is how `blacksail` read *settle: c9_1_s7 not built after 180 s* with four boots on four cores (Session 1764).

**What changed.** Each poll calls `tickCells(1)` before running the queue, as `g.cells` already does, and only in the open world
(`lid === 'overworld' && activeZoneId === 'world'`), so a suite that settles from indoors cannot have a room's coordinates read as the
world's. No check changed. This PR touches `tests/lib/`, so it waits for Michael's tap; for every other PR it changes nothing but how
fast a settled site appears (CI runs one boot a runner, where the game's own frames were nearly always enough).
