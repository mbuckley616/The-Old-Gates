## v80 — Session 1672 — `shuttle` waits for the loop's count, not 2.5 s (QA)

The systems builder's post for Sessions 1670–1671 named `shuttle` as failing twice on its wall-clock wait for the Cold and then
passing 3/3 on the same code. The check is *the main loop counts it on its own*: the suite moves the game's clock on a week and
leaves the game's own loop to count it, with a fixed `waitForTimeout(2500)` between. `tickShuttle` is throttled to once a second
of real time (`performance.now()`) and runs only when a frame does (`90-main.js`), so on a loaded runner, where a frame of the new
look takes seconds on software GL, 2.5 s could hold no counted frame. The game is right; the wait was the test's.

The suite now waits for what it waits for: `page.waitForFunction` until `worldState.cold` differs from the count before, polled
every 100 ms, up to 60 s, and the time it took is logged as `waited`. The check is unchanged and still asks for exactly one week
counted (`c0 + 1`) and the hub's line.

### Verified (headless Chromium)
- `shuttle` 3/3 green, 9/9 checks each, three side by side with `budget` running on the same four cores: the loop's count came
  after 3,530, 3,563 and 21,038 ms. Two of three would have failed on the old 2.5 s; the third by eight times over.
- No CI red on any check run in the last 40 green PR runs (no *failed, then passed on the retry* annotation either): the flake
  has only been seen locally so far. Row added to `docs/qa/flaky.md`, three CI runs green owed before it is called fixed.
