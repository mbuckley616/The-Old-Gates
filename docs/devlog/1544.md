## v80 — Session 1544 — twelve suites' `g.spin(<n>)` now tick the world (QA)
Session 1543 found that `g.spin(30)` in `jobfoereload` ran no tick: the harness's `g.spin` is `(weather, frames)`
(`tests/lib/game.mjs`), so a lone number is taken as the weather, the loop runs zero times, and `WORLD.wx.type` is set to that
number. Twelve other suites made the same call, 19 times: `barberchair` (`spin(10)`, `spin(4)`), `chairstash` (`spin(6)` twice),
`fortbarracks`, `forthall` and `fortring` (`spin(30)` after the fort's load, `spin(3)` before each picture), `lairdoor`,
`lairmaster`, `lairtheme` (its loop of 40 × `spin(30)` "until the job queue is empty" ran no jobs; the queue emptied by the real
loop between calls), `newelstair`, `oldsaves` (`spin(20)`), `shelfbook` (`spin(10)`, `spin(3)`, `spin(20)`) and `tierlevelfree`.
Each passed because the game's own loop ran frames between the suite's evaluates, which on a slow runner is the kind of race the
flaky ledger keeps finding. Each call is now `g.spin(null, <n>)`: the ticks the suite asked for, at the weather it already had.
Inside a dungeon `WORLD.tick` returns at once as before, so the fort and lair calls made in a dungeon are unchanged in effect.

No check was changed or loosened. A guard in `g.spin` itself (a lone number taken as frames, or a throw on a non-string weather)
would stop the next one, but `tests/lib/` is a pipeline file and waits for Michael's tap; it is owed to a later QA run of its own.
