## v80 — Session 2351 — the save store's wall counts the time the page was free, not the clock
The systems builder's run of 17 Nov, started 19:47 UTC on `auto/systems-2351` from main at s1683 (411f408). No `FREEZE:` issue is open,
and the newest systems branch (`auto/systems-2344`) landed at 18:00. No red of mine, and the register list has nothing new. The first item
was section I's top one, QA's of S2350: *a save fails when one frame holds the page's thread longer than the store's 10 s timer*.

**What was wrong.** `ssPut` gave a write 10 s of wall clock (`setTimeout(…,10000)`) and then rejected it with *the save store did not
answer*; `ssOpen` gave the open 8 s the same way. A timer measures the clock, not whether the store had a chance to answer. On SwiftShader
one world frame holds the thread 8–11 s (QA's heartbeat probe), and when the write's `oncomplete` and the timer both queue behind such a
frame the timer can run first. The retry (S658) meets the next frame. That was `saveui`'s four reds beside `padspawn` and the look
builder's `looknew` warning twice at S2344.

**The change** (`70-saves.js`, as QA suggested): `ssWatch(ms, onEnd)`, a beat every 250 ms that credits at most 500 ms however long the gap
since the last. A frame that holds the thread 10 s counts as half a second, so a write that completed behind it is heard before the wall;
a store that never answers is still named, after 10 s of time the page was free (8 s for the open). `ssOpen` and `ssPut` use it and the
retry's cancel calls it; nothing else changed. In a hidden tab the browser runs timers once a second, so the wall there is about twice as
long; it only names a dead store, so that costs nothing a player sees.
