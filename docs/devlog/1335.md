## v80 — Session 1335 — a save made inside a gate keeps what you killed, opened and unlocked (card F5, `gatesave`)
The last of F5's session 4 for the systems builder. The build sheet's "Saves" line: no new `worldState` key; a gate rebuilds from its
seed; what is opened, taken or killed is keyed `<seed>:<floor>:<index>` (the co-op rule); a load inside puts you at the entrance. The
entrance half was already so (Session 1283). The other half was not: a save made in the Dungeon of Shadows with half its foes dead
came back with all of them standing and every chest full, because the gate is built again from its seed and nothing said otherwise.

- **Foes have ids.** Each foe a dungeon places carries `id`, its `<seed>:<floor>:<index>` (the `fid` its spawn roll was already
  seeded from, Session 514's rule), so the same foe has the same id in every build of that gate. Containers and locked doors already
  had theirs (`<seed>:<floor>:chest:<n>`, `:barrel:`, `:door:`).
- **The save made inside carries them** (`dunGone`, `68-dungeon-misc.js`): the `where` record a save writes for a dungeon gains
  `gone`, the ids of the foes dead, each opened container with what is left in it, and the doors unlocked. It is in the save made
  inside and nowhere else, so no `worldState` key, no S242 list, no `SS_CHAR_WS`; leaving the gate forgets it, as a gate always has.
- **A load lays them so again** (`dunApplyGone`): `_reenterPlace` hands `gone` to the portal, and `goToDungeon` applies it the moment
  `buildDungeon` returns, behind the fade. A dead foe is dead and off the floor, an opened chest open with only what you left in it
  (its lid up), a door unlocked open and its cell passable.

Any dungeon with these ids is covered, forts and lairs too; a foe placed outside the spawn list (a lair's master, an ambush) has no
id and is built fresh, as before (the master's death is already kept by `slayMaster`). A key picked up and not used is not kept: it
lies where it lay, to be taken again.
