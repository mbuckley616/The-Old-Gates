## v80 — Session 1171 — Main's full runs no longer cancel each other

The pipeline (PR #459, Michael's A) promises that main runs every suite after each merge and that the next merge never cancels that run, and `check.yml` tried to keep it with `cancel-in-progress: false` for everything but pull requests. That is not enough. A GitHub concurrency group holds one running run and one pending run, and when a third arrives the pending one is cancelled, whatever `cancel-in-progress` says. Every main run was in the one group `check-refs/heads/main`, so on a busy afternoon each merge's run waited behind the one running and was then cancelled by the next merge's. Of the six main runs since #459 landed at 16:44 UTC, five were cancelled while pending: 6871654 (17:01), e343522 (#452, 17:18), 82c7d46 (#414, 17:48), ba34c3a (#455, 17:55) and 6210ccf (#462, 18:32). Only 7233261 finished, and ec52ee3 (#458) is running; 9718476 (#461) is pending and would have been the next to go. So four merges, Systems' among them, had no full run of their own, and a red on main could no longer be traced to the merge that caused it.

The fix is the concurrency key. A pull request's runs still share `check-<branch>`, so a new commit cancels its branch's older run as before. Every other run (a merge's dispatch from the automerge workflow, a push to main) takes `check-run-<run id>`, a group of its own, so nothing can cancel it. The cost is runners: main runs now overlap instead of collapsing into one, about 20 headless jobs each, and they queue alongside the pull requests' jobs. On today's pace (a merge every 10 to 30 minutes, a full run of about an hour wall time) that is two or three main runs at once at the busiest. If that starves the pull requests, the cheaper fix is a main run per merge at most every N minutes, which is Michael's call; this change keeps the promise as written. It is a pipeline change, so the PR waits for his approval, and it changes nothing for any other PR except the queue.

Main's one completed full run since #459, 7233261, was red on `guardplay` (shard 11, failed twice: `f1 {ticks:174, hp:0}`, the guard's light-then-heavy blow killing before the yield). That commit predates Session 1158's pin of the guard's minute (1295df7e, landed with #452 in e343522), so it is the bug already filed in I, which Michael answered A on #456 (the blow stops at the yield line). The systems builder owns the fix. Whether the pinned suite passes on main is for ec52ee3's run to show.

### Verified (headless Chromium)
No suite changed and none was run: the change is to the workflow alone. The concurrency key parses as YAML and reads the two cases as intended (`check-<branch>` on a pull request, `check-run-<id>` otherwise). The cancellations above are from the Actions API: workflow 367307281's runs on main since 16:44 UTC, each `cancelled` with no job started, its `updated_at` the minute the next merge's run was created. The proof is owed to the next busy afternoon: two merges in an hour should each show a full run.
