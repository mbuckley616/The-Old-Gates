## v80 — Session 1384 — one seed, one gate: the dungeon's shuffles made deterministic
*Renumbered from Session 1378: the bodies builder's trolls landed on main as `docs/devlog/1378.md` while PR #685 held the same file, so #685 went into conflict and could not merge. This run carries #685's change onto `auto/systems-1384` with the entry, the comments and the backlog line renamed; the second commit of #685 (the fort suites' pictures put back) is dropped, since the pictures are main's unchanged. #685 is closed for it. The code is the same.*

The look builder found it in passing in Session 1377: `makeGate('small', 57)` laid a different map on its second call in a page than on
its first, while the generator's other gates came out the same twice. Under the co-op rules a gate rebuilds from its seed, and what is
opened, taken or killed in it is saved by `<seed>:<floor>:<index>`. A gate that lays itself two ways can put a saved chest's index on
another chest, and a host and a friend could stand in different gates of one seed.

**The cause.** It reproduced only after other gates had been laid in the page (twenty tiny gates first, then small 57 three times: the
first differed from the second, the second matched the third). Every roll in `makeGate` and `dunAfterLayout` comes from the gate's own
stream, and the inputs to `dunAfterLayout` (the map, the rooms, the side rooms, the seed) were identical on both calls. What differed was
how many numbers the stream gave: 304 on the first call and 312 on the second, the same values up to the 304th. Three shuffles in
`dunAfterLayout` were `array.sort(()=>r()-.5)`: the side rooms the treasure rooms hang off, the four sides tried for each, and the
corridor cells that take the unlocked doors. A comparator that answers at random breaks the contract `sort` relies on, and how many
times an engine calls it is the engine's business: it changed with what V8 had run before in the page (wrapping `sort` in a JavaScript
function made the fault vanish), and Firefox's sort would call it differently again. So the treasure rooms and doors moved, and with
them the key places.

**The fix** (`52-dungeon-gen.js`): `dunShuffle(a, r)`, a Fisher–Yates shuffle on the stream, beside `dunLcg`, used at the three places.
It draws exactly `n − 1` numbers for `n` items whatever ran before, as `gateBlock`'s own shuffle already did. `dunAfterLayout` is shared by
`makeDungeon` and `makeGate`, so every dungeon, fort, lair and gate goes through it. The only other random comparator in `js/` is the
yard's watchers who shout for the captain (`87-world-quests.js`), which is cosmetic and stays.

**What moves.** Every dungeon's and gate's treasure rooms, unlocked doors and key places are now laid from a different (but fixed) use
of the same stream, so they are not where they were on the first visit of a page before this build. The spaces, side rooms and
chapels are laid before these shuffles and do not move. A save made in an older build that flagged a chest or a door by index may find
that index on another one; since the old layout already changed with what the page had built first, those indices were not reliable
anyway.
