## v80 — Session 1230 — Basic tests: the smoke set on a pull request, every suite once a week (CI, pipeline)
Michael, in chat, on learning that every suite boots the whole game: "This is a game I am making for fun, and do not plan to
ever charge for. We don't need bulletproof testing in this manner. Why can't we just have basic tests?" He took the
recommendation: the smoke set on every pull request, every suite once a week. He asked for the same in every game.

Where the time went:
- **The full run.** 522 suites came to 709 runner-minutes. Main ran it after each merge, on 20 shards, for about 70 minutes,
  in the account's one pool of runners (shared with Airsoft, whose own full run is ten shards).
- **The queue.** Pull requests waited 8 to 31 minutes behind each full run before a suite started (the last 12 green runs).
- **The suites themselves.** Each boots the game, makes a character and walks into the world on software GL before its first
  check. CLAUDE.md's step 5 made every session add one, so the count grew by one a session.

What changed:
- **`tests/lib/select.mjs`:** a pull request runs the smoke set (`looknew`, `saves`, `resolver`, `player`, `dungeon`,
  `autosave`) and any suite it adds or edits, in 6-minute shards (two for the smoke set alone). A docs-only PR runs none.
  The selection by the names a change reaches is gone, and with it `tests/lib/toplevel.cjs`.
- **`.github/workflows/check.yml`:** no run on a push to main. Every suite runs on Sunday at 06:00 UTC, and on any branch
  when `check` is run by hand.
- **`scripts/automerge.mjs`:** after a merge it starts `stamp` only, not `check`.
- **CLAUDE.md:**
  - Step 5: verify by running the area's suites, or a throwaway check in `tests/tmp/`. Add a suite only for something that
    would hurt to lose unnoticed. A picture for Michael is not a suite.
  - "How a PR lands": the producer files the weekly run's reds in section I, and nothing is reverted for them.
- **`docs/pipeline.md`:** says the same.

### Verified
