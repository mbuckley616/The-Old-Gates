## v80 — Session 1689 — the gate's web is drawn from both sides of the mouth it hangs in (`gatedraws` green)
The look builder's run of 1 Nov, first item: backlog section I's `gatedraws` red (QA, Session 1685). The cull promises that a gate drawn by zone
(`dRender`) and the same gate drawn whole differ by no pixel under a flat light. That failed at the large gate's (909) first threshold, 0.034%
of the frame, and at the massive gate's (2055) ring on floor two, 0.004%. The suite's culprit search named nothing.

**What it was.** A probe hid the cull's pieces in halves until one piece was left. In both gates it was a web (`gateWeb`, Session 1675). A web
hangs across a side room's one bare mouth, 0.25 m inside the room's edge cell. `dZoneOf` gives a piece its zone from its bounds, and calls it
"in two" (always drawn) only if its bounds reach a second zone. A web's bounds are a plane with no thickness, and it lies inside the room's cell,
so it was the side room's alone. The side room is drawn only when a sightline from your cell reaches one of its cells' middles. From the
threshold, none did, but the web in the mouth was in plain view through it. So the web vanished and the dark room behind it showed: 260 pixels at
909, 33 at 2055. The suite's own search had missed it because it tried only the first 80 pieces the cull hid, and there were 147 and 322.

**The change** (`gateThingsBuild`, `56-dungeon-build.js`). A web is given its zone record when it is built, marked as in two, with its bounds'
radius and height (`m._dz`, read by `dZoneOf` as it reads a measured one). So the zones never hide a web, and it is still hidden when it lies past
the fog. It is one draw, and a gate has 0 to 3 webs. In `gatedraws` the culprit search now tries every hidden piece, not the first 80 (a test change).
